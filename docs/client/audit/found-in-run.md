# Найденное в боевом прогоне

Сессия 15 августа 2026, после слайса 8. Человек включил бота на настоящих
каналах с поднятой LM Studio и смотрел, что происходит. Здесь — всё, что
всплыло, в порядке находок.

Отличие от [found-by-eye.md](found-by-eye.md): там расхождения вида, найденные
глазами на неподвижном окне; здесь — поведение под нагрузкой, которое видно
только на живом прогоне и не ловится ни одним нынешним тестом.

Улики брались из двух журналов сразу: `%APPDATA%\JobBot\jobbot.log` и окна
Developer Logs самой LM Studio. Порознь ни один из них картины не даёт.

---

## 1. Бот выключал сам себя, пока модель работала

**Исправлено** — `client/bridge/system.py`, коммит `9ae7d54`.

Улика из журнала приложения:

```
12:01:21  Bot mode changed: DM Only -> Full
12:01:36  Poll cycle start: 19 named channels (1 active)
12:01:36  [@django_jobs] 73789 -> vacancy 1
12:01:53  Bot mode changed: Full -> Off      ← через 17 секунд, сам
12:01:53  Bot mode changed: Full -> Off      ← и дважды за 13 мс
```

Лампочка спрашивала модель настоящей генерацией (`check_model` шлёт запрос с
`max_tokens: 1`), а LM Studio обслуживает одну модель по очереди: пока идёт
разбор вакансии, пробное обращение стоит в этой очереди. Общий десятисекундный
срок на обе модели истекал, ответом уезжало `(False, False)` — то есть гасли обе
лампочки разом, даже та, до которой очередь вообще не дошла, — и окно на красную
лампочку отвечало делом: `shouldTurnOff` слал `set_mode('Off')`.

Дальше выключение рвало запрос, шедший к модели в этот самый миг:

```
12:05:03  Bot mode changed: Full -> Off
12:05:08  validate_vacancy_fit: запрос не дошёл: RemoteProtocolError
12:05:08  validate_vacancy_fit unavailable for vacancy parse, marking Not Fit
```

То есть вакансия получала **Not Fit не по содержанию, а по оборванному
запросу**. В окне LM Studio это выглядело как `[LM STUDIO SERVER] Client
disconnected` при нормально завершившейся генерации — рвал соединение не сервер,
а мы сами.

В прежней оболочке на Qt такого срока не было вовсе: здоровье уезжало в окно
отдельным сигналом и ничьего ответа не задерживало (`client/bridge/state.py` до
слайса А2.9а). Срок появился вместе с переездом на pywebview, где здоровье едет
одним ответом с режимом и счётом непрочитанного.

Починено снятием нужды в сроке: пробы после первой уходят в сторону, лампочке
отдаётся прошлый ответ. Первую ждём — до неё не известно ничего, а «не знаю»
лампочка показать не умеет, и «мёртв» на первом ударе часов погасил бы бота,
поднятого в Full.

## 2. Пилюля статуса вакансии не открывала список

**Исправлено** — `client/web/components/StatusPicker.svelte` и
`client/web/app/VacancyCard.svelte`, коммит `9ae7d54`.

Окошко закрывалось «нажатием мимо», и своим узлом считало **само себя**, а
кнопка ему не принадлежит — она сосед внутри `.status-wrap`. Один клик успевал
сделать всё: открыть окошко, дать его `$effect` повесить сторожа на `document`,
дойти туда всплытием и быть сочтённым «мимо». Снаружи — ненажимающаяся кнопка.

Остальные восемь всплывашек проекта живы потому, что их узел «мимо» — обёртка,
внутри которой лежит и кнопка (образец — `ActionsMenu.svelte`). `StatusPicker`
был единственным исключением.

## 3. Подсказка имён моделей рисовалась движком

**Исправлено** — `client/web/components/SuggestInput.svelte`, коммит `9ae7d54`.

Поле модели было `<input list>` с `<datalist>`, и панель под ним рисовал сам
движок: свой кегль, своя рамка, чёрный треугольник внутри поля. Оформлением до
неё не достать. Заменено своей панелью классами `Dropdown`; отбор имён —
`matchingModels` в `client/web/state/settings.js`.

## 4. «Прогнать сейчас» отвечает отказом на любом обходе длиннее минуты

**Не исправлено.**

```python
# client/bridge/system.py:119
status = await bot.force_poll_once()
```

`force_poll_once` доходит до `backend/bot/slot.py:54`, где стоит
`await bot._current_poll_task` — ожидание **всего обхода целиком**. А ответ моста
сдаётся через минуту (`REPLY_SECONDS = 60.0`, `client/bridge/answer.py:26`) и
уезжает конвертом `{"fail": "timeout"}`. Обход при этом продолжает идти, и
человек видит плашку отказа над работающим сбором.

На модели `qwen3-4b-2507` одна вакансия проходит конвейер за две с лишним
минуты:

```
12:37:56  [@devs_it] 5640 -> vacancy 6
12:40:17  [@devs_it] 5642 -> vacancy 7    ← 2 мин 21 с спустя
```

То есть кнопка врёт **на каждом нажатии**, а не изредка.

**Что делать.** Не ждать обход в зове моста. `run_in_slot` решает «занято» в
первой же строке, а всё остальное окно и так узнаёт вестями —
`ingestion_started`, `progress_update`, `ingestion_finished` уже разведены в
`client/bridge/lifespan.py`. Отдавать приговор места сразу и отпускать обход
идти своим ходом.

## 5. Отказы `timeout` и `cancelled` уезжают без объяснения

**Не исправлено.**

```python
# client/bridge/answer.py:113, 116
return {"fail": "cancelled"}
return {"fail": "timeout"}
```

Это единственные два конверта во всём мосте без поля `detail`, и единственные, о
которых мост не пишет в журнал ни строки. Окно на такой конверт подставляет
запасную фразу (`client/web/api/bridge.js:76`):

```js
throw new Refused(fail, detail ?? 'Не получилось.', fields);
```

Человек читает «Не получилось.» и не узнаёт ни что случилось, ни что делать, а в
журнале о происшествии нет вообще ничего. Тот отказ, в который упираются чаще
прочих, объясняет себя хуже всех.

**Что делать.** Дать обоим свою фразу и запись уровня WARNING с именем работы —
ровно так, как это уже сделано у ветки `broken` рядом.

## 6. Окно гасит бота молча

**Не исправлено.**

```js
// client/web/app/Shell.svelte:138
if (shouldTurnOff(fresh, mode)) await pickMode(OFF);
```

Ни плашки, ни следа. След не появляется и на питоновской стороне: `set_mode`
пишет в журнал только при смене значения (`backend/runtime_settings.py:447`), а
окно при открытии само сбрасывает режим в Off (`client/window.py:140`) — то есть
авто-гашение поверх уже выключенного невидимо совсем.

Отсюда же ловушка для того, кто будет разбирать следующую такую беду: **молчание
журнала о режиме не доказывает, что записи не было.** В этой сессии на него
купился и разбор, и его пришлось поправлять.

Косвенная улика, что путь боевой: две записи `Full -> Off` в 13 миллисекундах
(12:01:53) — обе посчитали `prev=Full`, то есть `applyHealth` отработал дважды, и
счётчика неудач перед гашением нет никакого.

**Что делать.** Гасить с плашкой «почему» и со строкой в журнале.

## 7. Блокировка записи держится поперёк зова модели

**Не исправлено. В этом прогоне не стреляло.**

`backend/flows/parse_write.py` открывает сессию и правит строку вакансии, не
сбрасывая её; следом `find_or_create_company` делает `select(Company)`
(`backend/repository/companies_matching.py:453`), и автосброс SQLAlchemy
отправляет `UPDATE vacancy` — блокировка записи SQLite взята. С ней на руках
ждётся LLM-арбитр, а срок клиента — 180 секунд (`adapters/lm_studio.py:24`).

Любая другая запись в этот момент упрётся в `PRAGMA busy_timeout=5000`
(`adapters/db.py:49`) и через пять секунд получит «database is locked». В прогоне
не выстрелило только потому, что арбитра ни разу не звали — компании сходились
по имени.

**Что делать.** Либо решать компанию до открытия сессии, либо закрыть выборку
`session.no_autoflush`, чтобы правка вакансии не сбрасывалась раньше арбитра.

## 8. Промпт разбора не влезает в контекст модели

**Не наша поломка, но последствие наше.**

Окно Developer Logs у LM Studio:

```
send_error: task id = 1530, error: request (8788 tokens) exceeds the available
context size (8192 tokens), try increasing it
[qwen/qwen3-4b-2507] Error: Channel Error
```

Системный промпт `PARSE_VACANCY_PROMPT` — 23 975 символов, около 9600 токенов;
`VALIDATE_VACANCY_FIT_PROMPT` — столько же. С текстом объявления (до 6000
символов) и ответом реальный потолок обоих — 12–14 тысяч токенов. Модель,
загруженная с контекстом 8192, отбивает запрос мгновенно, не начиная генерацию:
отсюда и «промпты обрабатываются за миллисекунды».

Лечится настройкой загрузки в LM Studio: контекст не меньше 16384, лучше 32768.

Но последствие стоит записать: отказ провайдера доезжает до
`validate_vacancy_fit`, а тот считается несостоявшейся проверкой, и вакансия
получает **Not Fit**. То есть настройка чужого приложения молча портит приговоры
в нашей базе. Стоит подумать, верно ли «проверку не удалось провести»
приравнивать к «не подходит».

## Чего эти находки стоили тестам

Ни одна из восьми не была поймана набором, и причины у этого разные.

**Здоровье (1).** Ветка `except TimeoutError` не покрыта ничем: все тесты
лампочки ходят через `httpx.MockTransport`, который отвечает мгновенно. Тест с
именем `test_a_slow_provider_is_not_asked_twice_at_once` медленного поставщика не
заводит — он руками выставляет `_models_in_flight`. Закрыто новым тестом
`test_a_busy_provider_does_not_put_out_the_lamp`: на прежнем коде он падает ровно
за 10.88 секунды, то есть на самом сроке.

**Пилюля и подсказка (2, 3).** Покрыть нечем: в `client/web/vite.config.js`
стоит `test.environment: 'node'`, DOM в тестах нет, ни один тест не монтирует
`.svelte`. Весь слой разметки, событий и зовов моста не проверяется структурно —
баги этого рода набор не ловит в принципе, и обе починки держатся на чтении кода.

**Остальные (4–7).** Проверяются только на живом прогоне: нужен настоящий обход
длиннее минуты, настоящая очередь у поставщика и настоящая блокировка базы.
Ничего из этого нынешний набор воспроизводить не умеет.
