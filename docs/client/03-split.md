# Этап 3. Разбиение моста на файлы

`client/bridge.py` — 4468 строк при пределе манифеста в 500. Этап режет его в
целевую раскладку — домены плюс инфраструктура, — а не в промежуточную под Qt:
канал всё равно меняется, а 197 тестов этапа 2 написаны без окна и без канала и
переезд переживут.

**Только разбиение.** Разгрузка моста (63 сессии базы, `httpx`, `pypdf`,
вычисления) и повторы — это этап 4; переписывание фронта — свой этап. Здесь
код переезжает по файлам и не меняется по существу.

## Решение о технике: примеси

`MainApi` — один `QObject`, зарегистрированный в канале под именем `api`, с 74
сигналами и 90 слотами. Фронт зовёт `api.request_vacancies(...)` и подписывается
на `api.vacancies_changed` — значит поверхность обязана остаться одним объектом
с теми же именами, иначе этап 3 тянет за собой правку `main.html`.

Проверено опытом на PySide6 6.11.0: **сигналы и слоты, объявленные в обычном
классе-примеси, попадают в мета-объект наследника целиком.**

```
class DomainMixin:            # обычный класс, не QObject
    dom_sig = Signal(str)
    @Slot(str)
    def dom_slot(self, payload): ...

class Api(DomainMixin, QObject): ...

# staticMetaObject: ['own_sig(QString)', 'dom_sig(QString)',
#                    'own_slot(QString)', 'dom_slot(QString)']
```

Отсюда раскладка: каждый предмет — свой файл с классом-примесью, несущей **свои**
сигналы и свои слоты; `MainApi` собирает примеси и держит только общее —
конструктор, подъём бота, диспетчеры, уборку.

**Грабли, на которые наступили на слайсе 8.** Сигнал, объявленный и в примеси, и
в `MainApi`, попадает в мета-объект **двумя** записями. Питоновский `emit` берёт
последнюю, а `QWebChannel` публикует в JS первую — сигнал перестаёт доходить до
окна, и **197 тестов моста этого не видели**: они подписываются из питона той же
дорогой, что и `emit`. Вынося слоты, надо снимать и их сигналы.

Сторож заведён слайсом 9 — `tests/client/test_bridge_surface.py`: он считает
записи мета-объекта обеих поверхностей и требует, чтобы ни одна не встречалась
дважды. **Пропажу он не ловит** — для этого нужен снимок полного списка имён, и
завести его стоит на этапе 4, когда поверхность перестанет двигаться. Рядом с ним стоит второй тест, показывающий, что задвоенное объявление
и правда даёт две записи, — иначе первый сторожил бы неизвестно что. Красной
фазы у этой пары не было: она пришла к уже работающему коду, и доверие
зарабатывает итоговым проходом этапа.

## Целевая раскладка

Пакет `client/bridge/` вместо файла. Шов по предметам взят тот же, что у 197
тестов этапа 2, — файл теста ложится на файл кода один к одному.

| Файл | Что там |
|---|---|
| `runner.py` | `AsyncRunner` — цикл asyncio в своём потоке |
| `answer.py` | конверт ответа окну: `_ok`, `_err`, отправка сигналом |
| `payload.py` | жалоба в журнал на негодную нагрузку из окна |
| `wire.py` | перевод внутренних значений в словари для окна |
| `choices.py` | просеивание пришедшего из окна по известному набору |
| `media.py` | адрес вложения и аватар как `data:`-строка |
| `cv_file.py` | что можно узнать о файле резюме с диска |
| `state.py` | общее: первичное состояние, режим, сбор, здоровье, непрочитанное |
| `profile.py` | анкета, навыки, опыт |
| `cv.py` | выбор, замена и открытие резюме |
| `desktop.py` | просьбы окна к рабочему столу: ссылка и буфер обмена |
| `vacancies.py` | список, карточка, заметки, статус, пояснение к истории |
| `vacancy_actions.py` | перезапуск разбора, отправка отклика, удаление |
| `vacancy_links.py` | подборщики HR и компаний, привязка, создание из подборщика |
| `hr.py` | список, карточка, слияние, удаление, чёрный список |
| `hr_chat.py` | переписка: сообщения, отправка, вложения, прочтение |
| `companies.py` | компании целиком |
| `channels.py` | список, карточка, вакансии канала |
| `channel_actions.py` | опрос, сброс курсора, создание, удаление, включение |
| `blacklist.py` | чёрный список и подсказки к нему |
| `stats.py` | показатели |
| `journal.py` | системный журнал |
| `settings.py` | настройки и выход из Telegram |
| `llm.py` | проверка модели и список моделей |
| `login.py` | вход в Telegram — примесь, общая окну и мастеру |
| `wipe.py` | удаление всех данных |
| `wizard.py` | `WizardApi` — окно первого запуска |
| `main_api.py` | сборка примесей, конструктор, подъём бота, диспетчеры, уборка |
| `__init__.py` | поверхность пакета: `MainApi`, `WizardApi`, `AsyncRunner` |

**Хвост, который едет вместе со своим кодом.** Записка о слотах, отдающих
секреты в открытом виде, лежит в шапке пакета: правило о новых таких слотах
общее для всего моста, а перечень самих слотов расходится по `wizard.py`,
`profile.py` и `settings.py` вместе с ними.

**Логика в обработчике, оставленная этапу 4.** Долг унаследованный, но после
разбиения он виден отдельными файлами, и чинить его надо там же, где будут
сводиться повторы:

- `state.py:_kick_health` сам ходит в базу (`SELECT 1`) и в сеть — то есть
  обработчик события считает вместо того, чтобы позвать умеющего;
- `vacancies.py:request_vacancies` держит в теле слота четыре разборщика
  нагрузки, собирает отбор из шестнадцати полей и делает четыре запроса в базу;
- `hr_chat.py:request_contacts_hr_messages` сам разбирает дату из нагрузки;
- слоты чёрного списка в `companies.py` читают запись мимо репозитория и сшивают
  два репозитория в теле слота;
- `channels.py:request_contacts_channel_vacancies` собирает диагностический
  `select(func.count(...))` прямо в слоте — единственная причина, по которой
  файл вообще ввозит `select`, `func` и `Vacancy`;
- `blacklist.py:request_create_blacklist` сшивает в теле слота два репозитория:
  заводит запись отсева и тут же гасит попавшие под неё каналы;
- `journal.py:request_system_logs` — весь отбор, счёт уровней и схлопывание
  `CRITICAL` в `ERROR` живут прямо в теле слота;
- `wipe.py:request_delete_all_data` — крупнейший случай во всём пакете: в теле
  слота закрывается движок базы, удаляются файлы, чистится `keyring` и
  вызывается `os._exit`;
- `settings.py:save_settings` пишет постоянную в чужой модуль (`SEND_LOCKED`), а
  `request_telegram_logout` ждёт разрыва связи таймингом;
- слоты чёрного списка в `hr.py` и `channel_actions.py` — точные близнецы уже
  записанного случая из `companies.py`, причём канальный вдобавок сам правит
  `is_active` в теле слота;
- разборщики нагрузки в теле слота есть не только у вакансий: те же в `hr.py` и
  `companies.py`; `vacancies.py` вдобавок открывает вторую сессию базы.

**Мёртвое, найденное по дороге и оставленное этапу 4.** `_read_cv_text`
(`cv_file.py`) зовёт только `WizardApi._do_cv_parse_and_save`, а того не зовёт
никто: разбор резюме в мастере отключён, и ветка `mode == "parse"` отвечает
отказом. Дом под чтение файла заведён по ответственности, а не по числу
потребителей; сносить обе стороны — работа дедупликации, не разбиения.

**Порядок переезда.** Первым слайсом заводится пакет: весь нынешний мост
переезжает в `main_api.py`, инфраструктура выносится сразу. Дальше каждый слайс
вынимает из `main_api.py` один-два предмета. До последнего слайса `main_api.py`
остаётся выше предела — это переходное состояние, и закрывается оно внутри
этапа.

**Почему у одних предметов есть файл действий, а у других нет.** Критерий один:
файл действий заводится, когда чтение и запись вместе переваливают за предел.
У вакансии и у канала так и вышло. У человека и у компании делить нечего,
поэтому чёрный список у них лежит в файле карточки — не по решению о предмете.

Шов при этом не «чтение против записи»: у канала он такой, а у вакансии в
`vacancies.py` осталось три записи — заметки, статус и пояснение к истории. Там
шов прошёл между «правкой полей карточки» и «действием над самой вакансией»
(перезапуск разбора, отклик, удаление), и это разные швы. Свести их к одному —
работа не разбиения.

**Чего этап не решил.** `state.py` соединяет показ общего состояния окна с
управлением сбором, и шов тестов там уже разошёлся: `trigger_ingestion` и
`stop_ingestion` сторожит `test_bridge_vacancy_actions.py`. Одной фразой без «и»
этот файл не описывается — делить его надо, но не переездом, а вместе с
разгрузкой обработчиков на этапе 4.

**Почему выход из Telegram лежит в настройках, а не рядом со входом.**
`TelegramLoginSlots` — примесь, общая окну и мастеру, а выход есть только у
окна: он не просто рвёт связь, а останавливает бота и ждёт его завершения.
Мастеру этого механизма не нужно, и утащить выход в `login.py` значило бы
принести туда бота.

**Где шов тестов не совпал с швом кода.** Обещание «файл теста на файл кода»
держится не везде: `trigger_ingestion` и `stop_ingestion` сторожит
`test_bridge_vacancy_actions.py`, а `request_unread_chats` —
`test_bridge_hr_chat.py`, хотя код обоих уехал в `state.py`. Тесты этап 3 не
переписывает: они писались этапом 2 по экранам, а не по файлам.

**Что придётся тронуть в тестах.** Три места лезут в модуль напрямую и переедут
вместе с кодом: `from client.bridge import _iso` (`test_bridge_answer.py`),
`from client.bridge import _filter_set` (`test_bridge_choice_sets.py`),
`bridge.QDesktopServices` и `bridge.QApplication` (`test_bridge_shell.py`).
Правится путь доступа, не проверка. Все три поправлены слайсами 1 и 3.

## Замер на конец этапа

Один файл на 4468 строк стал пакетом из 29 файлов на 5016 строк. Прирост в 548
строк — это 29 шапок с ввозами и докстроками плюс 19 объявлений примесей; ни
одного тела слайсы не переписывали.

| Что | Было | Стало |
|---|---|---|
| Файлов | 1 | 29 |
| Крупнейший файл | 4468 (`bridge.py`) | 404 (`hr.py`) |
| Сборка поверхности | там же, где предметы | 286 строк, ни одного `@Slot` |
| Файлов сверх предела 500 | 1 | 0 |
| Тестов моста | 197 | 199 |

`main_api.py` держит ровно то, что обещала раскладка: конструктор, подъём бота,
три отправки работы на мотор, уборку и два сигнала, которые испускает бот, а не
предмет. Предметы приходят девятнадцатью примесями.

**Единственное изменение поведения за этап** — дробные имена журналов. Было одно
`client.bridge` на весь мост, стало по имени файла (`client.bridge.settings` и
так далее). Видно это в столбце «источник» на экране журнала; фильтров по имени
нигде нет, а разбирать записи стало легче.

**Что осталось незаведённым:** `_logs_request_last_ts` не заводится ни в одном
конструкторе — держится на `getattr` с умолчанием. Долг унаследованный, но
после разбиения он единственный такой в пакете.

## Повторы, подтверждённые по дороге, — этапу 4

Найдены рецензентами по картам, обе стороны каждого перечитаны в коде. Здесь
только запись, чтобы этап 4 не искал их заново: разбиение повторов не сводит.

- **`WizardApi.list_models_for` и `LlmSlots.request_llm_models`** — слот написан
  дважды целиком, вплоть до тела корутины; расходятся адресатом сигнала
  (`models_listed` против `llm_models_listed`), и оба имени знает фронт. Тот же
  шов, что у входа в Telegram, но свести его молча нельзя: общее имя сигнала
  правит и разметку;
- **выбор файла резюме** — заголовок диалога и перечень расширений выписаны
  дословно у `WizardApi.pick_cv_file` и у `MainApi.pick_cv_file_main`, а сам
  перечень обязан сходиться с `cv_file._read_cv_text`. Дом — `cv_file.py`;
- **мини-строка вакансии** выписана трижды — у человека, у компании и у канала:
  один тип на входе (`vacancies_mini`), одни пять ключей, одни запасные
  значения; лишний `posted_at` у канала окном не читается. Это четырнадцатый
  сборщик, которому место в `wire.py`;
- **постановка предмета в чёрный список** — **семь** тел: четыре зова «завести»
  (`hr.py`, `companies.py`, `channel_actions.py`, `blacklist.py`) и три
  «погасить» (`hr.py`, `companies.py`, `channel_actions.py`). Все зовут одно и
  то же объявление репозитория (`create_blacklist` и
  `deactivate_blacklist_values`, род строкой), а выбор написания уже сведён в
  `blacklist_marks` — разъезжается оправа вокруг них. Единственный дом —
  `client/bridge/blacklist.py`;
- **заслон «значение не может быть пустым»** написан слово в слово в мосте и в
  `backend/repository/blacklist.py`, причём мостовой не добавляет ни одного
  случая. Дом — репозиторий;
- **`set_blacklist_active` и `set_channel_active`** — полные близнецы, вплоть
  до строки `action="set_active"`. Чтению пары «номер плюс признак» дом —
  `payload.py`;
- **«правим только присланные поля»** — три написания (`blacklist.py`, `hr.py`,
  `companies.py`), и третье уже разошлось: отвечает «Неверные поля» вместо
  «Нечего обновлять.»;
- **«строка уже заведена»** решается двумя разными правилами: хранилище
  сравнивает точно, окно — без учёта регистра, и комментарий рядом утверждает о
  хранилище неверное. Рядом: проверка рода в двух слоях разными правилами,
  перечень родов в окне трижды при живом `BL_KIND_ORDER`, знание «`keyword` без
  подсказок» тремя телами в окне;
- **«канал в чёрном списке не работает»** — пять тел и четыре механизма: одни
  правят `is_active` вручную, другие зовут
  `channels_repo.deactivate_blacklisted_channels`. Дом есть — репозиторное
  объявление, оно же несёт объявленное чтение отметки;
- **заслон «канал в чёрном списке нельзя включить»** написан дважды в разных
  слоях: в `channel_actions.py` и в `backend/repository/channels.py`. При этом
  репозиторное `set_channel_active` заслона не имеет вовсе, а две его докстроки
  утверждают обратное — кодом это не подтверждается. Остаться должно
  репозиторное объявление; `blacklist.py` встаёт ровно на этот шов;
- **«Бот ещё не готов.»** — шесть тел в `channel_actions.py` и
  `vacancy_actions.py`, и они уже разошлись: два без `action`, так что окно не
  знает, какая кнопка отказала. Дом — `answer.py`;
- `channels.py` держит собственный SQL по вакансиям канала мимо репозитория —
  единственный такой ввоз во всём пакете моста;
- **«HR не найден», «Канал не найден», «Компания не найдена»** — пятнадцать тел
  той же семьи, что и «Вакансия не найдена»;
- **мини-список вакансий предмета** — у компании и у человека близнец **весь
  слот**, а не только строка. Канал в пару не входит: у него постраничность и
  своя диагностика;
- **подборщик предмета** написан четырьмя телами: пара подборщиков слияния
  (`companies.py` и `hr.py`) и пара подборщиков привязки (`vacancy_links.py`).
  У пары слияния различий нет ни одного, включая своё правило «поглощаемого не
  показывать»; прежний вердикт `not-duplicates.md` её не покрывал — оговорка
  там стояла без чтения и теперь снята;
- **`link_vacancy_hr` и `link_vacancy_company`** — тела дословны, включая
  правило «`null` значит отвязать»;
- «Нечего обновлять.» двумя телами без `action`; лестница исходов отправки
  текста и файла в `hr_chat.py`; фикстура мастера заведена в тестах дважды;
- **пять слотов статистики** совпадают знак в знак, кроме двух имён — пары
  «модуль.чтение» и сигнала; предметно не различается ничего. Сводить надо
  **тело**: сами пять имён обязаны остаться методами со `@Slot(str)`, иначе окно
  не найдёт их через канал. Та же пятикратность продолжается за каналом — в
  `main.html` лежат ещё десять тел той же формы;
- **`journal.py`** пишет потолок кольца числом мимо `log_buffer.MAX_RECORDS`,
  держит второе написание `repository/search.matches_search` (уже разошедшееся
  на краях и на не-строках) и одно из четырёх тел правила «CRITICAL считается
  ERROR'ом» — два из четырёх лежат прямо в нём, ещё два на JS;
- **ожидание остановки бота** написано дословно дважды — в `settings.py` и в
  `wipe.py`, — а третье тело (`main_api.cleanup`) разъехалось на пять секунд;
- **устройство каталога данных** выписано в `wipe.py` вторыми телами: имя файла
  базы против `config.py`, имена `sessions` и `media` против
  `adapters/telegram.py` и `backend/bot/media.py`. Переименуй кто-нибудь файл
  базы — «Удалить всё» молча оставит её на диске. Дом — `config.py`;
- **набор настроек, которые окну разрешено писать**, выписан дважды внутри
  `settings.py`: в снимке и в белом списке записи;
- **проба поставщика модели** написана двумя телами — `wizard._make_llm_check` и
  `LlmSlots.request_llm_probe`. Всего же правило о поставщике живёт
  **четырнадцатью телами в четырёх файлах**: чтение тройки из нагрузки — восемь,
  снимок окну — четыре, список моделей — пять, «модель жива» — четыре. Дом
  оконных — `llm.py`, дом правила «модель жива» — `adapters/lm_studio`, куда обе
  ветки здоровья в `state.py` пишут мимо;
- **«отправить корутину на мотор и разобрать исход»** — три тела
  (`answer._dispatch_json`, `main_api._dispatch_noop`, `wipe._on_done`), и
  третье уже разошлось: ловит только `Exception`, а `CancelledError` наследует
  `BaseException` — отменённый снос не отдаст окну ничего и не дойдёт до выхода
  из приложения;
- правило кэша ника написано дважды; в стенде — пары `catch_up_everyone`/
  `_catch_up` и `chatting`/`ready_to_send`;
- **правило постраничности** выписано четырьмя телами, и поведение у них уже
  разъехалось; **разбор даты из окна** — двумя;
- близнецы `chat_save`/`embed_save`, четыре одинаковых словаря настроек
  поставщика, чтение тройки его полей семью телами, близнецы веток здоровья
  чата и эмбеддингов, два одинаковых `_dispatch`;
- внутри `wire.py` правило «привязанное сильнее разобранного» написано дважды —
  в карточке вакансии и в строке списка;
- **проверка модели в здоровье** (`state.py:_kick_health`, обе ветки)
  переписывает первую половину `adapters/lm_studio.py:_check_model`: тот же
  `list_models` без рода и та же проверка вхождения. В адаптере выбор «без
  рода» объяснён комментарием, в мосте сделан молча. Остаться должно адаптерное
  объявление — но звать `check_*` целиком из здоровья нельзя, часы бьют раз в
  пять секунд. Третье, мелкое тело того же разговора — `llm.py`;
- **перевод исходов прогона в слова** написан дважды: в `state.py` и в слоте
  опроса канала; строка «Уже идёт другой цикл, попробуйте позже.» совпадает
  дословно, а устройство вокруг уже разъехалось;
- **«Телеграм на связи»** решается двумя разными правилами: в `state.py` — с
  `bot.is_ready`, в `settings.py` — без него;
- **чтение обязательного текстового поля формы** написано вручную четырьмя
  строками в `profile.py:save_profile`, хотя дом уже есть —
  `backend.payloads.text_or_none`, и вторая сторона (`client/form_payloads.py`)
  зовёт его. Тот же файл ввозит это объявление под псевдонимом `_none_if_empty`
  для необязательных полей: одно действие в одном теле двумя способами.
  Написания уже разошлись на ложных не-строках. Ещё три тела того же правила —
  в `cv.py`, `wizard.py` и `main_api.py`;
- отказ «Сначала сохраните профайл (CV-таб).» вместе с чтением анкеты написан
  дословно дважды в `profile.py` — предмет там один, анкета, а не навыки против
  опыта;
- **чтение строки из нагрузки** — одиннадцать тел, и они уже разошлись между
  собой; дом есть, `backend.payloads.text_or_none`. Рядом: `_list` против
  `backend.payloads.str_list` — одно правило, разъехавшееся на краях и на
  не-строках, и три тела чтения целого;
- **связка «жалоба в журнал плюс отказ „Неверные поля“»** — сорок восемь тел.
  Половина жалобы уже вынесена в `payload.py`, а вторая половина осталась в
  телах, и там же **текст исключения уходит в окно**, хотя от журнала его
  прячут нарочно;
- **«Вакансия не найдена.»** — девять тел, и номер эхом идёт то под ключом
  `id`, то под `vacancy_id`;
- **создание человека и компании из подборщика** — близнецы `contacts_create_hr`
  и `contacts_create_company`;
- **нагрузка подборщика собрана дважды на каждый предмет** внутри
  `vacancy_links.py` — при открытии и при заведении из него. Форма обязана
  сходиться, её кладут в один сигнал, а держат её два тела, и расхождение уже
  живое: на несуществующей вакансии открытие отвечает отказом, а заведение —
  успехом с пустым `current_id`;
- **три отказа формы заведения** написаны дословно дважды — в `vacancy_links.py`
  и в карточках контактов. Правило уже сведено в `form_payloads.py`, а слова
  остались в телах; заодно разъехалась обвязка записи компании: `commit()` без
  `begin()` и широкий `except` в одном месте против `session.begin()` в другом;
- хвост `Future` в трёх телах с разошедшимся правилом про отмену; часовые на JS
  в `main.html`, повторяющие `hr_is_identified` и `read_company_spellings`.
