# Спека: Claude для чата и эмбеддинги из файла модели

## Цель

Приложение работает без LM Studio и без второго ключа:

- чат-модель — Claude (по умолчанию предполагается Sonnet) через официальный SDK Anthropic;
- эмбеддинги — GGUF-файл модели, который приложение загружает само, в своём процессе.

Обе возможности — **надстройка**. Нынешний путь через OpenAI-совместимый сервер (LM Studio,
Ollama, OpenAI, OpenRouter) работает как сейчас, без изменений в поведении и в коде пути.
Промпты и их пределы в `backend/llm/*` не трогаются.

## Часть 1. Адаптер Claude

### Что видит человек

- В мастере и в настройках чата есть пресет «Anthropic»: адрес `https://api.anthropic.com`,
  поле ключа.
- После ввода ключа список моделей подтягивается сам, как сейчас у LM Studio: всё, что
  доступно этому ключу (Sonnet, Opus, Haiku).
- Кнопка проверки связи и лампочка CHT работают так же, как для любого другого поставщика.
- Для шага эмбеддингов галочка «тот же адрес и ключ, что у чата» при Anthropic недоступна:
  эмбеддингов у Anthropic нет.

### Как выбирается адаптер

- Признак — адрес поставщика: хост `api.anthropic.com`. Модель тут не годится: её выбирают
  из списка, а список уже надо спрашивать у Anthropic.
- Развилка стоит в точках входа в адаптеры:
  - создание клиента;
  - разговор с моделью;
  - список моделей;
  - проверка модели;
  - закрытие клиента.

  Всё, что за развилкой у нынешнего пути, не меняется.
- Схема базы не меняется: строка `llm_config` kind=chat хранит адрес, ключ и модель как сейчас.

### Что адаптер делает внутри

Наружу отдаётся тот же `ChatAnswer`, что у нынешнего пути. Различия Claude остаются внутри
адаптера:

- **Системный промпт.** Сообщения с `role: system` из `ChatRequest.messages` уходят в
  параметр `system`, остальные — в `messages`.
- **`temperature` не отправляется.** На текущих Sonnet и Opus значение не по умолчанию даёт 400.
- **Размышление включено** (адаптивное); глубина — `output_config.effort`. Уровень выбирается
  замером (см. ниже).
- **Предел токенов.** Размышление расходует `max_tokens`, поэтому пределы 1200–2400 из
  `backend/llm/*` (подобраны под локальную модель) адаптер поднимает до своего. Величина —
  по замеру. Константы в `backend/llm/*` остаются как есть.
- **Ответ** собирается из текстовых блоков; блоки размышления отбрасываются.
- **Признаки окончания:**
  - `stop_reason: "max_tokens"` отдаётся как `finish_reason: "length"`, чтобы нынешняя
    жалоба на обрыв и решения зовущих работали без правок;
  - `stop_reason: "refusal"` становится `ChatAnswer(error=...)` и записью в журнал с
    категорией отказа.
- **Ошибки SDK** превращаются в те же строки `error`, что у нынешнего пути: `llm_http_error: <код>`
  для ответа с кодом, `llm_request_error: <тип>` для недошедшего запроса. Откаты зовущих
  работают без правок.
- **Время ожидания** — то же, что у нынешнего пути (180 с). Повторы при 429 и 5xx — встроенные
  в SDK.
- **Список моделей** — `models.list()` SDK. Для рода `embed` — пустой список.
- **Проверка модели** — модель есть в списке плюс пробный однословный запрос. Для рода
  `embed` — отказ с понятной фразой: у Anthropic нет моделей эмбеддингов.

### Замер перед выбором уровня размышления

Делается до того, как уровень зафиксирован в коде:

1. Взять около десятка живых вакансий из базы.
2. Прогнать на Sonnet нынешние запросы — жанр, разбор, три проверки пригодности, письмо,
   проверку письма — при `effort` low, medium и high.
3. По каждому прогону записать время, расход токенов и ответы. Сравнить уровни между собой
   и с ответами локальной модели.
4. По итогу выбрать уровень и предел токенов.

Если окажется, что разным запросам нужен разный уровень, — это отдельное решение человека:
оно потребует отдельного поля в `ChatRequest`, то есть правки за пределами адаптера.

### Зависимости и сборка

- `anthropic` в Pipfile, версия закреплена.
- PyInstaller подхватывает SDK. Если что-то нужно, дописать в `hiddenimports` в `JobBot.spec`.

### Тесты

- Подделка ответов в форме Anthropic: текст, обрыв по пределу, отказ, ошибка HTTP, недошедший
  запрос, список моделей.
- **Запор сети распространяется на SDK.** SDK ходит через свой HTTP-клиент, мимо нынешних
  httpx-подделок. Тестовый стенд обязан не пускать тесты к настоящему API, и
  `tests/test_harness_safety.py` это проверяет.

## Часть 1б. Claude через Claude Code по подписке

API Anthropic оплачивается отдельно от подписки. У человека подписка Max, поэтому основной
путь к Claude — установленный Claude Code в режиме без окна (`claude -p`) под его входом.
Адаптер API (часть 1) остаётся рядом и годится, если когда-нибудь появится ключ.

### Что видит человек

- Пресет «Claude Code (подписка)». Адрес — служебное слово `claude-code`, ключа нет.
- Список моделей — `sonnet`, `opus`, `haiku`: эти имена Claude Code понимает сам и ведёт к
  последней версии.
- Проверка связи — пробный запрос через Claude Code. Лампочка CHT горит, если Claude Code
  установлен.

### Как устроено

- Признак — адрес `claude-code`. Развилка — в тех же точках входа, что у адаптера API.
- Запрос — отдельный процесс `claude.exe -p`. Флаги:
  - `--output-format json`, `--model`, `--effort`;
  - `--system-prompt-file` — системный промпт из временного файла;
  - `--tools ""`, `--no-session-persistence`, `--setting-sources ""`, `--strict-mcp-config`,
    `--disable-slash-commands`.

  Текст обращения уходит через stdin. Рабочий каталог — временный, окно процесса не
  показывается.
- Ключи `ANTHROPIC_API_KEY` и `ANTHROPIC_AUTH_TOKEN` из окружения процессу не передаются:
  Claude Code с ними ушёл бы на оплачиваемый API мимо подписки.
- Ответ — JSON. `result` — текст. Признак конца переводится, как в части 1. `is_error` с кодом
  API становится `llm_http_error: <код>`, остальные беды процесса (нет Claude Code, не
  запустился, вышел с ошибкой, не уложился в срок, ответ не разобрать) — `llm_request_error: <род>`.
- Срок ожидания — тот же 180 с или свой у обращения. По истечении процесс снимается.
- `.cmd`-обёртка npm ведёт к настоящему `claude.exe` рядом. Запускается он, а не обёртка.

### Что важно знать

- Лимиты подписки общие с интерактивной работой человека.
- Каждый запрос — запуск процесса, на вызов выходит около трёх секунд.
- Нужен установленный Claude Code с выполненным входом на той же машине.

### Тесты

- Запуск процесса — одна функция; стенд запирает её так же, как транспорт SDK.
- Проверяется то, что уходит в процесс (флаги, stdin, окружение без ключей), и разбор ответа:
  текст, обрыв, отказ, ошибка API, сбой процесса, срок.

## Часть 2. Эмбеддинги из GGUF-файла

### Что видит человек

- На шаге эмбеддингов (мастер и настройки) выбор: «Сервер» (как сейчас) или «Файл модели».
- В режиме «Файл модели» есть кнопка выбора файла (системный диалог, фильтр `*.gguf`) и
  показан выбранный путь. Поля адреса и ключа не нужны.
- Кнопка проверки связи загружает модель и считает пробный эмбеддинг.
- Лампочка EMB горит, если файл на месте.

### Как хранится выбор

- Схема базы не меняется. Строка `llm_config` kind=embed: адрес пустой, в `model` — путь к
  `.gguf`. Пустой адрес и путь в модели и есть признак локальной модели.
- Пустой адрес сейчас отбивается в двух местах:
  - чтение черновых учётных данных из окна (`client/bridge/llm.read_llm_creds`);
  - подъём настроек из базы (`backend/runtime_settings.py`, строка `if not row.base_url or
    not row.model`). Строка без адреса считается ненастроенной, `rs.embed` выходит пустым, и
    бот не стартует.

  В обоих местах пустой адрес законен для эмбеддингов, если модель — путь к файлу.

### Что адаптер делает внутри

- Движок — `llama-cpp-python`, сборка под процессор, без компиляции.
- **Загрузка ленивая**, при первом обращении: модель около 600 МБ, держать её незачем, пока
  бот не работает. Освобождается при остановке бота.
- **Расчёт — в отдельном потоке:** он синхронный и нагружает процессор, а asyncio-петлю бота
  стопорить нельзя. Обращения идут по одному: движок не рассчитан на одновременные вызовы.
- **Окно контекста** — с запасом под `_EMBED_MAX_CHARS` (6000 знаков) из `flows/embeddings.py`.
- Отдаёт `list[float]`, как нынешний `lm_embed.embed`.
- **Ошибки.** Нет файла или модель не загрузилась — это «поставщик молчит» в смысле
  `flows/embeddings.ProviderIsSilent`: обход канала останавливается, курсор не уезжает. Сбой
  на конкретном тексте — «не вышло на этом тексте», как сейчас.

  Сейчас `flows/embeddings._is_about_the_provider` различает эти случаи только по
  httpx-исключениям. Это единственная ожидаемая правка вне адаптеров и окна.

### Совместимость с векторами в базе

Сейчас эмбеддинги считает тот же файл (bge-m3 Q8_0) через LM Studio. Перед переключением
нужна ручная проверка: несколько текстов посчитать обоими способами и сравнить.

- Косинус около 1 — старые векторы остаются в деле, отсев повторов не теряет память.
- Заметно ниже — нужен прогон вакансий заново. Это решение человека.

### Зависимости и сборка

- `llama-cpp-python` в Pipfile, версия закреплена, готовое колесо под Python 3.13 и Windows.
  **Первым делом проверить, что такое колесо есть.**
- В `JobBot.spec` добавляется библиотека движка. Файл модели в exe не вшивается: onefile
  распаковывал бы 600 МБ на каждом запуске.

### Тесты

- Подделка движка: настоящая модель в тестах не грузится.
- Пустой адрес с путём к файлу принимается окном, пустой адрес без файла — отбивается.
- Отсутствующий файл останавливает обход канала, как молчащий сервер.

## Что не меняется

- Путь через OpenAI-совместимый сервер для чата и эмбеддингов.
- Промпты, их пределы и разбор ответов в `backend/llm/*`.
- Схема базы, порог отсева повторов, кэш векторов.
- Условие запуска бота (`client/bridge/lifespan._ready_for_bot`) не меняется. Оно выполняется
  и при новых поставщиках, если подъём настроек принимает строку embed с путём к файлу (см.
  «Как хранится выбор»).
