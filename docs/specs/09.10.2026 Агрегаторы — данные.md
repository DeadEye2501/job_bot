# Агрегаторы — данные

Первая часть работы по агрегаторам: схема базы, миграции и то, что в коде
обязано поменяться вместе со схемой, чтобы ничего не сломалось. Поток обхода,
агент, браузер, капча, вкладка и остальное окно — следующими спеками.

## Зачем

Кроме Telegram-каналов приложение будет искать вакансии на агрегаторах (hh.ru,
GetMatch и других) и откликаться на них агентом. Сейчас база знает только один
вид источника и один вид отклика — Telegram. Нужно место для:

- самих агрегаторов и отметки, вошёл ли человек на сайт;
- вакансий, пришедших с агрегатора, и отсева их повторов;
- контактов вакансии, которые не Telegram-HR (почта, ссылки, телефон);
- откликов, ушедших не в Telegram, и памяти о прочитанном в их чатах;
- скрининга на агрегаторах — вопросов работодателя и наших ответов;
- почты, с которой уходят отклики письмом;
- настроек обхода агрегаторов и поиска по сети.

## Что не меняется

- **HR.** Таблица `hr` и ссылка `vacancy.hr_id` как есть. В HR пишется только
  Telegram-контакт, и всё, что на нём держится, работает как работало.
- **Переписка Telegram.** Таблица `message` как есть. Telegram-отклики и
  Telegram-скрининг в новые таблицы не дублируются: они и так видны в чате с HR.
- **Каналы.** Таблица `telegram_channel` и `vacancy.source_channel_id` как есть.

## Новые таблицы

### `aggregator` — агрегатор как источник

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | |
| `name` | str, not null | как показывать: «HeadHunter» |
| `host` | str, null, уникальный индекс `uq_aggregator_host` | домен сайта в нормальной форме: `hh.ru`; пусто — это строка «Поиск по сети» |
| `is_active` | bool, not null, по умолчанию false | переключатель во вкладке, как у канала |
| `is_logged_in` | bool, not null, по умолчанию false | вошёл ли человек на сайт; пока нет — агрегатор серый и включить его нельзя |
| `last_run_at` | datetime, null | **начало** последнего завершённого обхода; пусто — обхода ещё не было |

- **«Поиск по сети» — особая строка этой таблицы** с пустым `host`. Её
  заводит схемная миграция, у любого человека она одна. Удалить её нельзя
  (держит код удаления), включить и выключить — можно. Входа у неё нет:
  миграция заводит её сразу с `is_logged_in = true`. Вакансии, найденные в сети,
  ссылаются на неё, как вакансии с hh — на строку hh: так у поиска по сети
  есть своя строка в статистике и свой отсев повторов.
- **Хост в нормальной форме:** нижний регистр, без схемы, без `www.`, без пути и
  косой черты в конце. Человек вводит адрес как угодно (`https://www.hh.ru/`),
  хранится `hh.ru`. Так один сайт не заводится дважды.
- **Чья ссылка.** Ссылка принадлежит агрегатору, если её хост равен его хосту
  или кончается на `.` + хост: `spb.hh.ru` — это `hh.ru`, `nothh.ru` — нет.
  Тем же правилом уже сравнивает `backend/domain/company_hosts.py`.
- **`last_run_at`.** Берётся начало обхода, а не конец: то, что выложили во
  время обхода, следующий обход ещё увидит. Обход, оборванный сбоем, метку не
  двигает. Пауза на капчу — часть обхода, а не его конец.
- **Входа в базе нет:** ни логина, ни пароля, ни куки — только отметка
  `is_logged_in`. Человек один раз входит на сайт руками в окне браузера,
  дальше работает сохранённый профиль. Отметку ставит и снимает агент,
  проверив сайт (спека потока). Новый агрегатор заводится выключенным и не
  залогиненным: включить его можно только после входа. Профиль лежит в
  каталоге данных: `browser/<aggregator.id>/`. Каталог `browser/` входит в
  `config.data_dirs()` — его сносит «удалить все данные». Удаление агрегатора
  удаляет и его каталог.
- **Пустой `host` — только у строки «Поиск по сети».** Окно добавления
  агрегатора адрес без хоста не принимает.
- **Удаление агрегатора** разрешено. Если у его вакансий есть отклики, окно
  спрашивает подтверждение с их числом. Вакансии остаются, ссылку на агрегатор
  у них и у откликов отвязывает код удаления — так же, как удаление канала
  отвязывает свои вакансии (`repoint_vacancies`).
- **`AGGREGATOR_HOSTS`** в `backend/domain/company_hosts.py` — другое понятие:
  перечень хостов, ссылка на которые ничего не говорит о компании. С таблицей
  `aggregator` не сливается и от неё не зависит.

### `vacancy_contact` — контакты вакансии, кроме Telegram-HR

Один-ко-многим к вакансии.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | |
| `vacancy_id` | int, FK → `vacancy.id`, not null | |
| `value` | str, not null | контакт как найден или введён: `HR@Company.ru`, `https://hh.ru/vacancy/123?from=main`, `+7 …` |
| `match_key` | str, not null | `value` в нормальной форме — по нему сравнивают |
| `added_by` | enum `parse` / `agent` / `user`, not null | кто завёл: разбор вакансии, агент-искатель со страницы вакансии или человек |

Индексы: уникальный `uq_vacancy_contact_key` (`vacancy_id`, `match_key`) и
`ix_vacancy_contact_match_key` (`match_key`) — для поиска вакансии по контакту
поперёк всех вакансий.

- **Нормальная форма** (`match_key`): нижний регистр; у почты убирается
  `mailto:`; у ссылки — схема, `www.`, параметры `utm_*` и `from`, косая черта в
  конце; у телефона остаются только цифры. Правило живёт в одной функции домена.
- **Вида контакта не храним.** Почта, телефон или ссылка — видно по значению;
  ссылка на агрегатор — по правилу «чья ссылка» выше. Форму от сайта
  работодателя по тексту не различить никому; это узнаёт агент, открыв ссылку.
- **«Прогнать заново»** заменяет только строки `added_by = parse`. Найденное
  агентом и добавленное человеком не трогается. Если разбор нашёл то, что уже
  есть с тем же `match_key`, остаётся прежняя строка, вторая не заводится.

### `application` — отклик не через Telegram

Одна строка на каждый раз, когда агент откликнулся вне Telegram: нажал
«Откликнуться» на сайте агрегатора, отправил форму работодателя, написал
письмо. Один-ко-многим к вакансии.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | |
| `vacancy_id` | int, FK → `vacancy.id`, not null | |
| `aggregator_id` | int, FK → `aggregator.id`, null | на каком агрегаторе, если отклик ушёл на нём |
| `via` | enum `aggregator` / `form` / `email`, not null | куда ушёл |
| `target` | str, not null | адрес страницы, формы или почты |
| `letter` | str, null | текст сопроводительного письма; пусто — ушёл без письма |
| `sent_at` | datetime, not null | когда отправлен |
| `chat_anchor` | str, null | якорь чата этого отклика на сайте — см. ниже |

Индекс: `ix_application_vacancy_id` (`vacancy_id`).

- **Отклик пишется только состоявшимся:** строка `application`, её скрининг и
  переход вакансии в Applied — одной транзакцией, после того как сайт
  подтвердил отправку. Сорвавшийся на полпути (капча, ошибка формы) отклик не
  оставляет ничего.
- **Чат и якорь живут на отклике, а не на вакансии:** на агрегаторе переписка
  открывается по отклику, и у двух откликов одной вакансии два чата.

#### Якорь чата

Хеш последних трёх сообщений чата отклика: сторона (мы / не мы) и текст, без
времени.

- При обходе агент ищет в чате три сообщения подряд с тем же хешем; всё ниже —
  новое и идёт на разбор ответа, после чего якорь сдвигается на новый хвост.
  Одинаковых троек несколько — берётся последнее вхождение.
- Сообщений меньше трёх — якорь считается по всем, что есть.
- Пустой якорь — чат ещё не читали: всё, что в нём от работодателя, — новое.
- Наша собственная реплика в чате (ответ на скрининг) сдвигает якорь той же
  записью, что сохраняет реплику.
- Текст чата не хранится. Что делать, когда якорь не нашёлся, решает спека
  переписки.

### `screening` — скрининг на агрегаторах

Вопросы работодателя и наши ответы, где бы их ни задали: в форме отклика до
отправки, в Google-форме, в чате агрегатора.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | |
| `application_id` | int, FK → `application.id`, not null | к какому отклику |
| `from_us` | bool, not null | true — наш ответ, false — вопрос или реплика работодателя |
| `text` | str, not null | |
| `position` | int, not null | порядок реплик внутри отклика |
| `created_at` | datetime, not null | когда записано |

Индекс: уникальный `uq_screening_position` (`application_id`, `position`).

- Где был задан вопрос, не храним: показывается всё одинаково — пунктом
  «Скрининг» в меню «⋯» карточки вакансии, отклик за откликом. Раскладка — в
  спеке окна.

## Изменения в `vacancy`

| Колонка | Тип | Смысл |
|---|---|---|
| `source_aggregator_id` | int, FK → `aggregator.id`, null | с какого агрегатора пришла вакансия |
| `source_key` | str, null | номер вакансии на источнике: путь адреса её страницы, `vacancy/123456` из `https://hh.ru/vacancy/123456?from=main` |

Индекс: уникальный `uq_vacancy_aggregator_key` (`source_aggregator_id`,
`source_key`) — он же служит индексом по `source_aggregator_id`.

- **Источник.** У вакансии заполнен не больше чем один источник:
  `source_channel_id` или `source_aggregator_id`. Обе пустые — вакансия
  вставлена текстом или заведена руками. Правило держит код записи (ограничение
  CHECK в SQLite потребовало бы пересборки таблицы).
- **Номер вакансии вынимает только код** — из адреса страницы, который даёт
  агент; сам агент номера не составляет. Для агрегатора это путь адреса без
  параметров и без косых черт по краям (`vacancy/123456`). Для поиска по сети —
  хост и путь (`company.ru/careers/python-dev`): сайты разные, и только адрес
  целиком отличает одну от другой. Если у агрегатора номер в адресе устроен
  иначе, правило под него дописывается в той же функции. При заполненном
  `source_aggregator_id` номер не бывает пустым — иначе уникальность его не
  ловит (в SQLite пустые значения не равны друг другу).
- **Отсев повторов.** Агент спрашивает «эта уже есть?» по паре «агрегатор +
  номер», не открывая вакансию. Повторы между разными источниками — та же
  вакансия из канала и с hh, с hh и с GetMatch, перевыложенная под новым
  номером — ловит существующий отсев по эмбеддингу. Изредка второй отклик на
  ту же вакансию допустим.
- **Удаление вакансии удаляет всё:** её контакты, отклики и их скрининг — там
  же, где сейчас удаляются лента событий и история статусов
  (`delete_vacancy`, `backend/repository/vacancies_life.py`). Если агент потом
  найдёт её снова, откликнется снова — так задумано.

### `mail_account` — почта для откликов письмом

Одна строка, по образцу учётки Telegram (`tg_account`). Даёт приложению только
отправку по SMTP — читать ящик оно не может и не пытается.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | int, PK | всегда 1 |
| `address` | str, null | с какого адреса уходят письма |
| `smtp_host` | str, null | сервер SMTP; для Gmail подставляется сам |
| `smtp_port` | int, null | порт; для Gmail — 465 |
| `password_encrypted` | str, null | пароль приложения, зашифрованный тем же Fernet, что `api_hash` Telegram |
| `updated_at` | datetime, not null | |

Пароль в журнал не попадает: поле добавляется в вымарывание
`backend/log_secrets.py`. Пустой `address` или пароль — почта не настроена,
отклик письмом недоступен, порядок отклика переходит к следующему способу.

## Настройки в `app_setting`

Новые ключи, без миграции — умолчания живут в `_APP_DEFAULTS`
(`backend/runtime_settings.py`):

| Ключ | Умолчание | Смысл |
|---|---|---|
| `aggregator_backfill_limit` | `20` | сколько новых для базы вакансий искатель передаёт в конвейер за обход одного источника |
| `show_browser` | `false` | браузер виден всё время; выключено — виден только на капче и входе |

Отдельной модели для агента нет: агента водит тот же поставщик и та же модель,
что выбраны для чата. `LlmConfigKind` не меняется.

## Изменения в `trash_event`

Отметка о мусоре сейчас знает только канал и номер сообщения. Добавляются
`source_aggregator_id` (FK → `aggregator.id`, null) и `source_key` (str, null).

- Мусор с агрегатора попадает в его строку статистики, а не в «Без канала».
- Искатель, снова встретив удалённое как мусор объявление, получает от
  `is_known` «уже было» и не тратит на него предел.

## Что меняется в коде вместе со схемой

- **Разбор вакансии** пишет найденный контакт (`other_contact`) в
  `vacancy_contact` с `added_by = parse`, а не строкой «Контакты: …» в `notes`
  (`backend/flows/parse_write.py`). Заметки остаются только человеку: разбор и
  «Прогнать заново» их больше не пишут и не стирают.
- **Карточка вакансии** показывает контакты отдельным блоком, где их можно
  добавить и удалить руками (`added_by = user`). Вид блока утверждает человек.
- **Поиск по вакансиям** ищет и по `vacancy_contact.value`
  (`backend/repository/vacancies_list.py`).
- **Статистика** до спеки потока относит вакансии с агрегаторов к строке «Без
  канала» таблицы каналов. Свои строки у агрегаторов и поиска по сети — в
  спеке потока.

## Миграции

Засевной миграции больше нет: она своё отработала и вынесена из `alembic/` в
`docs/seed/` (под git не идёт). Рабочая база разработчика уже стоит на `init`.

1. **Схемная миграция, в git** — следующая после `init`. Всё, что описано выше,
   плюс строка «Поиск по сети» (`host` пустой, выключена, `is_logged_in = true`):
   она нужна каждому. Любая база — новая и рабочая — получает её при старте
   приложения обычным `upgrade head`.
   - Новые колонки с внешним ключом добавляются в SQLite с
     `inline_references=True`; составная уникальность — уникальным индексом, а
     не ограничением: штатный ALTER в SQLite не умеет ни того, ни другого. В
     моделях — `Index(..., unique=True)`.
   - `JobBot.spec` перечисляет миграции поимённо: новая ревизия добавляется в
     `datas`.
   - Тестовый стенд поднимает схему до `INIT_REVISION` (`tests/conftest.py`):
     поднимать до новой ревизии.
2. **Перенос контактов — разово, вне git.** Сразу после того как рабочая база
   прошла схемную миграцию, скриптом из папки сессии, не из репозитория.
   Проходит по всем вакансиям: строка `notes`, начинающаяся с «Контакты: »,
   даёт одно значение — разбор пишет туда один контакт. Значение ложится в
   `vacancy_contact` с `added_by = parse`, строка убирается из заметок;
   остальной текст заметок не трогается. Строки, где после «Контакты: » стоит
   Telegram-ник (`@…`), не переносятся: Telegram — это HR.

## Что вне этой спеки

Поток обхода агрегатора, агент и его инструменты, браузер, пауза на капчу —
`09.10.2026 Агрегаторы — поток.md`. Чтение чатов откликов (отказ на сайте как
смена состояния отклика, запасной путь, когда якорь не нашёлся) — своей
спекой. Раскладка окна: вкладка «Агрегаторы», экран «Скрининг», окно выбора
способа отклика, настройки почты. Промпты и тексты писем — своей спекой.
