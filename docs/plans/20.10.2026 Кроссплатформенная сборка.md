# Предложение: сборка Job Bot для macOS и Linux

Дата плана: 20.10.2026. Обновлено: 21.10.2026. Статус: этап A (выделение Windows-модуля) выполнен; macOS и Linux ещё не реализованы.

План дополнен после сверки со [спецификацией macOS](../specs/20.10.2026%20Сборка%20под%20macOS.md). Принятые дополнения и отличия от неё перечислены в разделе 12.

## 1. Рекомендуемое решение

Порядок реализации: сначала выделить Windows-зависимости в отдельный платформенный модуль без изменения поведения Windows; затем реализовать и локально проверить macOS на Mac пользователя; только после этого приступить к Linux. CI и отдельная macOS-инфраструктура для этой последовательности не требуются.

Сохранить Python 3.13, Svelte/Vite, pywebview и существующий JS–Python bridge. Добавить отдельный модуль `build_tools/` на Python для подготовки окружения, сборки фронта, упаковки приложения и проверки артефактов. Необходимые различия во время работы приложения вынести в небольшой пакет `adapters/platforms/` с отдельными реализациями для ОС.

Основной упаковщик — PyInstaller: он уже используется проектом и позволяет включить интерпретатор Python в дистрибутив. Сборки выполнять на соответствующих ОС и архитектурах; это единый процесс сборки с несколькими целями, а не получение macOS/Linux-приложения из Windows exe. PyInstaller не является кросс-компилятором. [Документация PyInstaller](https://pyinstaller.org/en/stable/index.html).

Rust в первую версию не включать. Обоснование и условия пересмотра решения приведены ниже.

Одного нового сборщика недостаточно: некоторые текущие модули используют WinAPI уже при импорте. Минимальные изменения в коде приложения необходимы и для запуска из исходников, и для запуска упакованной версии.

## 2. Что изучено и как устроен проект

Изучены `README.md`, `Pipfile`, `Pipfile.lock`, `pyproject.toml`, `JobBot.spec`, `docs/maps/{module-map,data-map,front-map}.md`, текущие спецификация и план общего конвейера, точки входа и платформенные адаптеры, конфигурация фронта и связанные тесты. Карты используются как навигация: фактическое поведение проверено по исходникам, поскольку карты местами отстают от кода.

| Область | Текущее устройство | Вывод для переноса |
| --- | --- | --- |
| Запуск | `main.py`: замок, журнал, keyring, миграции, окно; также `--update` | Оставить точку входа, ограничить Windows-ветви |
| Backend | Python, asyncio, SQLAlchemy, SQLite/Alembic, Pyrogram | Переписывание предметной логики не требуется |
| Интерфейс | `client/window.py`, pywebview; `client/web/` — Svelte 5/Vite | UI уже имеет кроссплатформенную основу |
| Мост | `client/bridge/`, `client/web/api/{bridge,events}.js` | Сохранить договор вызовов и событий |
| Раздача UI | `client/serving.py`, локальный HTTP, пути через `__file__` | Сохранить структуру ресурсов внутри bundle |
| Браузер агента | `adapters/browser.py`, Playwright и отдельный обычный браузер для входа | Нужны платформенный поиск и перенос жизненного цикла |
| Данные | `config.py` уже учитывает Windows, macOS и XDG Linux | Не менять каталог и формат данных без необходимости |
| Секреты | `backend/crypto.py`, Fernet и системный keyring | Сохранить, обеспечить упаковку нужного backend |
| Сборка | Корневой `JobBot.spec`: Windows onefile, фронт, миграция, Playwright, llama_cpp | Использовать как образец состава, добавить отдельные spec |
| Тесты | pytest/pytest-asyncio, Vitest; много подмен внешних сервисов | Переиспользовать, дополнить реальными проверками ОС |

Предположение о Windows-компонентах UI верно частично: Windows использует WebView2, но сам pywebview поддерживает macOS и Linux. На macOS доступен WebKit через PyObjC; на Linux нужно выбрать GTK либо Qt. [Установка pywebview](https://pywebview.flowrl.com/guide/installation).

## 3. Подтверждённые препятствия

Таблица фиксирует исходные места обнаружения до рефакторинга. Перенос Windows-зависимостей выполнен на этапе A; актуальное соответствие файлов — в [build_tools/README.md](../../build_tools/README.md). Остальные платформенные реализации остаются задачами следующих этапов.

| Файл / функция | Проблема | Необходимое действие |
| --- | --- | --- |
| `Pipfile`: `llama-cpp-python` | Прямая ссылка на `cp313-win_amd64.whl` версии 0.3.19 | Разделить установку по платформам; другие цели получают wheel своей архитектуры либо сборку из исходников |
| `adapters/process_windows.py` | `ctypes.WINFUNCTYPE` вызывается на уровне модуля; `browser.py` импортирует `has_window` без условия | Убрать импорт Windows-реализации из общего пути запуска, загружать её только на Windows |
| `backend/single_instance.py:_BUSY` | `errno.EDEADLOCK` читается при импорте и отсутствует в проверенном окружении Darwin | Использовать доступную константу (`EDEADLK` на POSIX), сохранить Windows-коды; проверить именно Python 3.13 |
| `adapters/browser.py:find_browser` | Поиск через Windows-переменные окружения и пути `.exe` | Отдельные стратегии macOS/Linux |
| `adapters/browser.py:_window_closed` | Наблюдение за видимым окном через WinAPI | Ввести переносимый сценарий завершения ручного входа, см. раздел 7 |
| `adapters/app_tied_process.py` | Windows Job Object; на других ОС публичные функции фактически ничего не делают | Реализовать управление собственными процессами и проверить аварийное завершение отдельно |
| `adapters/browser.py:_launch` | Привязка драйвера по имени `node.exe` | Изолировать эту Windows-эвристику, использовать платформенную стратегию |
| `client/bridge/desktop.py:open_in_system` | Только `os.startfile`; на других ОС возвращает ошибку | Windows: прежний путь; macOS: `/usr/bin/open`; Linux: `xdg-open` |
| `client/bridge/desktop.py:_show_in_folder` | Запуск `explorer /select,` для файлов, которые запрещено открывать | macOS: `/usr/bin/open -R`; Linux: FileManager1.ShowItems либо открытие родительского каталога без запуска файла |
| `client/window_size.py:_unlock_frame` | После мастера безусловно импортирует `webview.platforms.winforms` | Платформенная реализация изменения рамки, минимального размера и растягиваемости |
| `client/trouble_box.py` | Только `MessageBoxW`, ошибка показа гасится журналом | Платформенный показ ошибки до создания основного окна |
| `backend/updater.py` | Копирование exe, WinAPI ожидания PID, Windows `creationflags` | Не вызывать этот механизм на macOS/Linux |
| `main.py:main` | `updater.clear_leftovers()` вызывается без проверки ОС | Ограничить Windows, чтобы не удалять посторонние `.new` рядом с POSIX executable |
| `adapters/github_release.py` | `ASSET = "JobBot.exe"` | На новых платформах не предлагать этот файл как обновление |
| `client/bridge/app_update.py:version/update` | Любая frozen-сборка считается обновляемой | Ввести явную возможность установки обновления; проверять её также на backend |
| `client/window.py`, `JobBot.spec` | `.ico` и Windows keyring hidden imports | Платформенные иконки и состав зависимостей |

`adapters/claude_code.py` содержит Windows-поиск `claude.exe`, но уже возвращает `shutil.which("claude")`, если соседнего exe нет. Это место требует проверки на реальном macOS/Linux, а не обязательного переписывания. Запуск из Finder/ярлыка может иметь другой `PATH`, чем терминал.

`config.py`, POSIX-ветвь `backend/single_instance.py` и условные WinAPI-вызовы в `client/raise_window.py` уже содержат полезную переносимость. Проверить их на целевых ОС, не заменять автоматически.

Дополнительная проверка показала конкретный дефект lock: записи `pywin32`, `pywin32-ctypes`, `pythonnet`, `clr-loader` не ограничены Windows-маркером, а `pyobjc-*` отсутствуют. Перенос установки нельзя ограничивать заменой wheel llama-cpp-python.

## 4. Инструменты и зависимости

| Назначение | Предложение | Комментарий |
| --- | --- | --- |
| Управление сборкой | Python, `argparse`, `pathlib`, `subprocess`, `venv`, `tomllib` | Стандартной библиотеки достаточно для CLI; без отдельного runtime |
| Упаковка Python | PyInstaller + `pyinstaller-hooks-contrib` | Зафиксировать проверенные версии в build lock |
| Упаковка macOS — резерв | py2app | Использовать, если короткий прототип выявит существенные проблемы PyInstaller/PyObjC |
| UI macOS | Существующий pywebview + PyObjC/Cocoa/WebKit | Системный WKWebView, без установки Qt |
| UI Linux | Существующий pywebview + GTK/PyGObject/WebKitGTK | Основной кандидат для небольшого дистрибутива; требует системных библиотек |
| UI Linux — резерв | Поддерживаемый pywebview Qt backend | Если GTK/Python 3.13 трудно воспроизводимо упаковать; оценить размер и лицензии |
| Нативные эмбеддинги | `llama-cpp-python==0.3.19`, CMake, Ninja, C/C++ toolchain | При отсутствии wheel собирать локально на текущем этапе; CI добавить позднее |
| Секреты Linux | `SecretStorage`/его зависимости, D-Bus, Secret Service | Для начальной поддержки — desktop с работающим хранилищем |
| Секреты macOS | Существующий keyring, backend macOS | Проверить discovery и доступ в подписанном `.app` |
| Фронтенд | Существующие Node.js, npm, `package-lock.json` | `npm ci`, затем `npm run build`; версию Node выбрать по engines закреплённого Vite |
| macOS-дистрибутив | Xcode Command Line Tools, `codesign`, `notarytool`, `stapler`, `hdiutil` | Для публичного выпуска — подпись и нотариализация |
| CI — последующее расширение | GitHub Actions либо аналог с нативными runners | Не требуется для локальной реализации и приёмки macOS |

Документация pywebview рекомендует py2app для macOS и PyInstaller для Windows/Linux. Поэтому единый PyInstaller — предлагаемое упрощение, которое нужно подтвердить прототипом macOS, а не считать уже проверенным официальным рецептом. Держать оба упаковщика постоянно без необходимости не требуется. [Упаковка pywebview](https://pywebview.flowrl.com/guide/freezing).

Набор и версии PyGObject/WebKitGTK согласовать с выбранным дистрибутивом и закреплённым pywebview. Системный `python3-gi` не обязательно доступен отдельному Python 3.13 из venv: не строить инструкцию на предположении, что одного `apt install` достаточно. Не копировать устаревшие рецепты Qt5/WebKit из документации без проверки.

### Почему сейчас без Rust

| Вариант | Преимущества | Цена для этого проекта |
| --- | --- | --- |
| Python CLI + PyInstaller | Совпадает с текущим стеком, сохраняет мост и UI | Нужны платформенные адаптеры и нативные сборки |
| Rust CLI, запускающий Python/Node | Самостоятельный исполняемый сборщик | Добавляет Cargo/toolchain; Python, npm и нативные зависимости всё равно нужны |
| Tauri 2 + Python sidecar | Rust-оболочка, средства упаковки, перспектива другого жизненного цикла | Перенос pywebview bridge/events, запуск backend отдельно, IPC, упаковка Python sidecar для каждой цели |
| Перенос backend на Rust | Полный контроль над runtime | Большая переработка интеграций, несовместимая с минимальным вмешательством |

Tauri действительно поддерживает sidecar, но требует отдельного бинарника под целевую платформу; сам по себе он не решает упаковку Python. [Документация Tauri](https://v2.tauri.app/develop/sidecar/). Вернуться к нему разумно при отдельной задаче замены desktop-оболочки. Для текущего контрибьюта выгоды Rust не компенсируют усложнение.

## 5. Границы изменений и структура новых модулей

Целевая структура. Windows-пакет и платформенные точки входа уже реализованы; `build_tools` пока содержит только документацию, CLI/spec новых ОС ещё не созданы. macOS/Linux-пакеты, ресурсы и workflow добавляются на своих этапах, а не все сразу:

```text
build_tools/
  __main__.py                 # CLI: doctor, build, verify
  config.toml                 # цели, форматы, версии инструментов
  dependencies.py             # сборка входного набора зависимостей
  frontend.py                 # npm ci / build
  freeze.py                   # запуск упаковщика
  artifacts.py                # архивы, manifest, SHA-256
  specs/
    macos.spec
    linux.spec
  hooks/                      # только отсутствующие штатные hooks
  locks/                      # разрешённые зависимости по целям
  assets/                     # .icns, desktop-файл, Linux-иконки
  README.md
adapters/platforms/
  __init__.py                 # выбор реализации без импорта чужого WinAPI
  windows/                    # этап A: существующий Windows-код по предметам
  macos/                      # этап B: реализации тех же функций
  linux/                      # этап C: добавляется после приёмки macOS
tests/build_tools/
tests/adapters/                # проверки платформенных контрактов
.github/workflows/
  desktop-build.yml
```

Не называть пакет `platform`, `packaging` или `build`: это создаёт пересечения с библиотеками и инструментами. Runtime не импортирует `build_tools`; пакет сборщика не включается в дистрибутив приложения. `adapters/platforms/` содержит только операции ОС, не бизнес-логику.

Первую итерацию сделать добавочной: сохранить корневой `JobBot.spec` и текущую сборку Windows. Новый CLI может делегировать ей Windows-сборку. Общую декларацию ресурсов извлекать после подтверждения новых сборок, если это действительно уменьшит дублирование.

Необходимые изменения существующих файлов:

- `Pipfile` и lock: сделать установку `llama-cpp-python` платформенной, добавить выбранные платформенные зависимости с markers. Прямой Windows wheel можно сохранить в Windows-ветви.
- `adapters/browser.py`: заменить Windows-поиск и наблюдение за окном вызовами платформенного слоя; сохранить управление агентом и профилями.
- `client/bridge/desktop.py`, `client/trouble_box.py`: делегировать операции ОС.
- `client/window_size.py`: вынести Windows-изменение рамки, добавить Cocoa и выбранный Linux backend; сохранить договор `grow_to_main`.
- `backend/single_instance.py`: устранить чтение отсутствующего `errno.EDEADLOCK` при импорте, сохранив семантику замка.
- `adapters/app_tied_process.py`: сохранить публичные функции, направить POSIX-поведение в отдельную реализацию; Windows-код не переписывать без причины.
- `client/window.py`: выбор иконки/backend, только если этого потребует прототип.
- `main.py`, `client/bridge/app_update.py`: ограничить Windows-обновлятор, в том числе очистку остатков и прямой вызов обновления.
- `adapters/claude_code*.py`: менять только по результатам проверки поиска executable и завершения процессов.
- Небольшая правка существующего UI/bridge для подтверждения ручного входа на Linux/Wayland, если потребуется сценарий из раздела 7; на macOS сначала проверить Quartz без изменения пользовательского сценария.
- `README.md`: добавить команды сборки, поддержанные ОС, особенности установки и обновления.

Менять модели данных, конвейер откликов, LLM-промпты, структуру Svelte-экранов и схему БД для самой переносимости оснований нет.

## 6. Зависимости и воспроизводимость

Сохранить текущие версии рабочих пакетов как исходную точку; не обновлять их массово ради переноса. В ходе исследования не выполнялась установка всех закреплённых пакетов, поэтому доступность каждой версии и wheel на всех целях ещё не подтверждена.

Предпочтительный источник зависимостей — существующий `Pipfile` с платформенными markers и отдельными проверенными locks для целевых окружений. Не вести второй вручную скопированный список рабочих пакетов в сборщике. Если один Pipenv lock не воспроизводит все цели, `build_tools` должен получать входные требования из `Pipfile`, явно обрабатывать прямой Windows URL и генерировать целевые locks. Зафиксировать команду их обновления и проверять рассинхронизацию в CI.

Нельзя просто дважды объявить один TOML-ключ `llama-cpp-python` в `[packages]` с разными markers: это невалидный TOML. Поддерживаемую Pipenv схему нужно проверить прототипом; если варианты одного пакета не выражаются корректно, использовать генерируемые платформенные входы/locks с одним общим источником требований. Установка без lock допустима для разведки, но не для релизной сборки. Проверять отсутствие Windows-only пакетов в macOS/Linux lock и наличие PyObjC либо выбранных Linux-зависимостей.

Отдельно закрепить инструменты сборки и транзитивные зависимости, сохранять хеши скачанных/собранных wheels. В manifest записывать commit, версию приложения, ОС/архитектуру, версии Python/Node/упаковщика, выбранный UI backend и режим llama.cpp. Это делает процесс повторяемым; побайтовая идентичность подписанных дистрибутивов отдельной целью не является.

Для llama-cpp-python сначала проверить наличие доверенного wheel под Python 3.13 и каждую архитектуру. При отсутствии собирать wheel версии 0.3.19 локально на соответствующей ОС и использовать проверенный результат; перенос этого действия в CI отложить до завершения локальной поставки. На Linux начать с CPU; на macOS — с CPU либо отдельно проверенного Metal. Не использовать сборку с инструкциями только CPU машины-сборщика. CUDA и прочие ускорители оставить отдельными вариантами после базовой переносимости. Официальный проект описывает сборку через CMake и варианты CPU/Metal; наличие конкретного wheel `cp313` всё равно проверяется отдельно. [Установка llama-cpp-python](https://llama-cpp-python.readthedocs.io/en/stable/).

Проверить также нативные зависимости `tgcrypto`, `greenlet`, `cryptography`, `numpy`, PyObjC/PyGObject. Пользователю готового приложения не должны требоваться Python, Node.js или компилятор. Браузер, Claude Code для соответствующих функций и файл GGUF остаются внешними, как сейчас.

## 7. Платформенное поведение, которое нужно спроектировать

### Браузер и ручной вход

Для macOS искать executable внутри системных и пользовательских `.app` (например, `Contents/MacOS/Google Chrome`); для Linux использовать `shutil.which` и проверенные типовые пути. Начальная проверенная поддержка — Chrome и при необходимости Chromium, затем расширение списка. Snap/Flatpak-обёртки не считать обычными бинарниками без проверки доступа к профилю. Нельзя оставлять в подсказке обещание поддержки всех браузеров Windows.

Сохранить отдельные профили под `get_data_dir()/browser`, не использовать личный профиль пользователя. Сохранить обычный браузер без Playwright для входа: текущий код специально делает это из-за ограничений Google OAuth. Браузер агента и WebView интерфейса — разные компоненты; WebKit на macOS не заменяет Chromium агента. Playwright документирует работу с Chrome/Edge и установку своего Chromium; произвольные браузеры требуют отдельной проверки совместимости. [Браузеры Playwright](https://playwright.dev/python/docs/browsers).

`has_window(pid)` нельзя переносимо заменить на `process.returncode`: Chromium может оставаться в фоне, а стартовая обёртка — завершаться раньше окна. На macOS сначала реализовать двойник через PyObjC/Quartz: `CGWindowListCopyWindowInfo` и `kCGWindowOwnerPID`. Проверить сопоставление с фактическим PID браузера, скрытые/свёрнутые окна и разные Spaces: отсутствие окна на текущем экране не должно ошибочно означать закрытие. Проверить доступность нужных метаданных без дополнительных разрешений. Это позволяет сохранить текущий сценарий без новой кнопки. [Список окон Apple](https://developer.apple.com/documentation/coregraphics/cgwindowlistcopywindowinfo(_:_:)), [PID владельца окна](https://developer.apple.com/documentation/coregraphics/kcgwindowownerpid).

У Wayland нет общего аналога WinAPI-перечисления чужих окон. Предлагаемый базовый сценарий Linux/Wayland: пользователь завершает вход кнопкой в приложении; приложение просит закрыть браузер входа, дожидается освобождения профиля и лишь затем передаёт его агенту. Нужны отмена, тайм-аут и понятный повтор при занятом профиле. Точное обнаружение освобождения профиля подтвердить прототипом; при сомнении не запускать второй процесс с тем же профилем. Windows сохраняет существующее определение закрытия окна; macOS переходит на этот fallback только при подтверждённой непригодности Quartz.

Не обходить задачу подключением CDP к обычному браузеру входа без отдельной проверки: это может вернуть исходную проблему автоматизированного входа. Сворачивание/подъём окна агента через существующий CDP проверить на macOS, X11 и Wayland; при ограничениях допустим явно описанный режим постоянно видимого браузера.

### Процессы и внешние программы

На POSIX использовать отдельные сессии/группы для собственных дочерних процессов, штатное завершение и ограниченное ожидание перед принудительным завершением группы. Не завершать чужие браузеры по имени executable. Отдельно проверить драйвер Playwright, обычный браузер входа, общий Claude Code и Claude Code агента.

Группа процессов сама по себе не обеспечивает уничтожение потомков при `SIGKILL` родителя. Проверить необходимость отдельного наблюдателя за каналом родителя; Linux-specific механизмы не переносить на macOS. Паритет аварийного завершения с Windows Job Object — отдельный критерий, который нельзя объявлять выполненным на основании нормального shutdown.

Для macOS конкретный кандидат — отдельный сторож с `select.kqueue`, `KQ_FILTER_PROC` и `KQ_NOTE_EXIT`, отслеживающий родителя и завершающий собственные группы. Проверить гонку регистрации, выход родителя до запуска сторожа, наследование дескрипторов и независимость сторожа от уничтожаемой группы. `SIGKILL` родителя сам по себе не исключает работу отдельного сторожа; гарантировать очистку при уничтожении самого сторожа или всей сессии нельзя. [Процессные события kqueue в Python](https://docs.python.org/3/library/select.html#kqueue-objects).

Для Claude Code сохранить сначала `shutil.which`, затем на macOS проверять известные пользовательские пути (`~/.local/bin/claude`, `~/.claude/local/claude`, `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`) с проверкой исполнимости. При необходимости добавить явный путь в настройках. Чтение PATH из login-shell — резервный вариант с тайм-аутом и обработкой вывода startup-скриптов; не менять глобальный PATH без необходимости. Отдельно проверить npm-установку: найденному скрипту может понадобиться `node` в окружении. Приёмка обязательна из Finder, а не только из терминала.

Для открытия файлов/URL запускать системные утилиты списком аргументов, без `shell=True`, сохраняя существующие ограничения схем, расширений и путей. Учитывать изменённое загрузочное окружение frozen-приложения: внешним системным программам может требоваться восстановление переменных поиска библиотек; bundled-драйверу Playwright — собственное окружение. Архивы должны сохранять POSIX-права и символические ссылки. [Ограничения PyInstaller](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html).

### Keyring и ошибки до открытия окна

В bundle включить backend macOS либо Linux SecretService и необходимые метаданные для discovery. На Linux требуется рабочая desktop-сессия D-Bus и разблокированное хранилище; CI с поддельным keyring не проверяет эту интеграцию. Начальный контракт Linux — Secret Service, поддержка KWallet напрямую оценивается отдельно. Не добавлять plaintext fallback. [Системные хранилища keyring](https://keyring.readthedocs.io/en/latest/).

Для стартовой ошибки на macOS использовать Cocoa-диалог; на Linux — диалог выбранного GTK backend. Если сама GUI-библиотека недоступна, необходимы понятный вывод в stderr при запуске из терминала и запись в журнал; необязательный `zenity` можно использовать только как дополнительный fallback. `tkinter` не считать автоматически доступным.

### Переход из мастера и особенности WebKit

`grow_to_main` должен не только увеличить окно, но и снять запрет растягивания, изменить минимум и сохранить положение центра. На macOS проверить `window.native` как NSWindow: `NSWindowStyleMaskResizable`, `setMinSize_`, изменение frame через Cocoa в главном потоке (`AppHelper.callAfter` либо проверенный механизм backend). Не смешивать координаты Cocoa и pywebview без проверки Retina/масштаба. Для Linux реализовать тот же контракт средствами выбранного GTK/Qt backend. Проверка обязательна для чистой БД: запуск с завершённым мастером этот дефект скрывает.

В WebKit проверить `field-sizing: content` в `chat.css` и `confirm-send.css` на минимальной поддержанной macOS; при отсутствии поддержки нужен существующий либо небольшой JS-autosize fallback. Проверить фактический CSS после Vite для `-webkit-user-select`, копирование через `navigator.clipboard.writeText` на локальном HTTP и метрики шрифтов. `-apple-system` уже есть в `base.css`, `SFMono-Regular`/`Menlo` — в `raw-text.css`: добавлять их повторно не требуется. Другие monospace-стеки менять только при выявленном дефекте. Cmd уже поддерживается в `state/keys.js`, нужна регрессия, а не новая реализация.

Иконку `.icns` получать из существующего `client/icon.png` через набор размеров и `iconutil`; Dock берёт её из `.app`, а не из `webview.start(icon=...)`. Проверить повторное открытие через LaunchServices и клик Dock после скрытия/сворачивания; существующий lock и `raise_window` сохранить для прямого запуска executable и других ОС.

### Обновления

Для первого контрибьюта сохранить самообновление Windows. На macOS/Linux установить `updatable=false`, запретить установку также на backend и не вызывать Windows updater ни по `--update`, ни при старте/очистке. Поле `frozen` не означает поддержку обновления.

На этих платформах обновление первой версии — ручная установка нового дистрибутива с сохранением каталога данных. Проверка релизов либо возвращает отсутствие поддержанного обновления, либо открывает страницу загрузки с артефактом своей ОС; не скачивает `JobBot.exe`. Если добавляется выбор артефактов, выбирать по ОС и архитектуре и сохранять проверку контрольной суммы. Автоматическую замену `.app`, каталога Linux или пакета менеджера вынести в следующую задачу.

## 8. Форматы поставки и CI

| Цель | Первая поставка | Среда сборки и ограничения |
| --- | --- | --- |
| Windows x86_64 | Прежний `JobBot.exe` | Контроль регрессии на доступной Windows-системе; runner необязателен |
| macOS, нативная архитектура Mac пользователя | Сначала `.app` в ZIP; DMG для последующего публичного выпуска | Локальная сборка и проверка на Mac пользователя, без подготовки runner/VM |
| macOS x86_64 | Отдельный `.app`/DMG после проверки зависимостей | Нужен соответствующий runner; universal2 не обещать |
| Linux x86_64 | PyInstaller onedir в `.tar.gz`, launcher и `.desktop` | Базовая проверка на Ubuntu 24.04 LTS desktop; системные GTK/WebKitGTK и Secret Service |

Это предлагаемая матрица, а не уже подтверждённый список совместимости. Перед фиксацией минимальных версий ОС проверить требования закреплённых Playwright, pywebview и нативных wheels. Сборка Linux должна происходить на самой старой поддержанной glibc-системе; поддержку других дистрибутивов расширять проверками. [Совместимость Linux-сборок](https://pyinstaller.org/en/stable/usage.html#making-gnu-linux-apps-forward-compatible).

На macOS начать с отдельных архитектур: universal2 требует совместимости всего набора нативных зависимостей. Упаковка и подпись dylib/вспомогательных исполняемых файлов требуют проверки. [Архитектуры и подпись PyInstaller](https://pyinstaller.org/en/stable/feature-notes.html#macos-multi-arch-support). Для публичного DMG выполнить подпись Developer ID, нотариализацию и stapling; локальный неподписанный прототип не считать готовым пользовательским релизом. [Нотариализация Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

В macOS spec явно использовать onedir + `BUNDLE(...)`, стабильный bundle identifier, `.icns` и Info.plist с `NSHighResolutionCapable`; проверить hook для `webview.platforms.cocoa` и PyObjC. `doctor` должен отличать нативный arm64 Python от x86_64 под Rosetta. Metal-вариант llama собирать с `CMAKE_ARGS=-DGGML_METAL=on` и проверять фактическую архитектуру и загрузку runtime-ресурсов.

Первый проверочный артефакт может быть `JobBot-macos-arm64.zip`, сохраняющий ссылки и права; DMG и подписанный выпуск — следующий шаг того же pipeline. Для пилота допустим явно обозначенный неподписанный артефакт с документированным системным подтверждением открытия. Не включать снятие quarantine через `xattr -cr` в установщик автоматически. Обязательность Developer ID/нотариализации относится к заявленному полноценному публичному выпуску, а не к сборке прототипа.

Не исключать Intel из перспективной матрицы только из-за вывода `macos-13`: текущая документация GitHub перечисляет `macos-15-intel` и arm64 `macos-15`. Начать с arm64, Intel подтверждать отдельной сборкой и тестированием. Runner label и доступность перепроверить при реализации workflow. [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

На Linux архив с системными зависимостями — сознательно ограниченная первая поставка. AppImage, `.deb`, Flatpak и Linux arm64 — следующие варианты после работающего onedir. AppImage не гарантирует совместимость со всеми glibc и WebKitGTK; Flatpak потребует проверки доступа к CLI, браузеру и keyring.

CI добавляется после локальных реализаций при необходимости. Будущий конвейер повторяет локальные команды: установка locked-зависимостей → pytest и Vitest → сборка фронта → упаковка на своей ОС → проверка состава и запуска → архив/DMG → manifest и SHA-256. Публикация релиза — отдельный явно запускаемый этап после проверки артефактов. GUI на Linux можно предварительно проверять через Xvfb, но Wayland, Finder, keyring и Gatekeeper требуют отдельных desktop-проверок. Secrets подписи не нужны для pull request от внешнего контрибьютора.

## 9. Последовательный алгоритм работ

Основной порядок: **архитектурное выделение Windows → реализация и локальная приёмка macOS → реализация и приёмка Linux**. Следующий этап начинается после закрытия предыдущего. Linux-код, Linux-зависимости и Linux-упаковку не разрабатывать одновременно с macOS.

Mac пользователя — доступная машина для локальной сборки и проверки. Отдельную macOS-машину, VM, runner или инфраструктуру CI для этого не готовим. Проверяем фактическую архитектуру и уже установленные инструменты; недостающие зависимости проекта устанавливаем только по необходимости. Начальная цель — нативная архитектура этого Mac; arm64 остаётся исходным предположением до проверки, а не поводом настраивать другую машину.

Каждый шаг ниже закрывается полученным результатом и указанной проверкой. Шаги 1–4 выполнены на архитектурном этапе; нативная Windows-регрессия отмечена отдельно как непроведённая. Шаги 5–19 не начаты. Разделы 1–8 описывают целевое устройство для обеих ОС, но не требуют реализовать их одновременно.

Нативная Windows-сборка/GUI/Job Object с этого Mac не проверялись и остаются открытыми до финальной передачи. Подробности — в [отчёте этапа A](../validation/21.10.2026%20Windows%20architecture.md).

4. Не вводить абстрактные классы, реестры и framework плагинов: достаточно функций с единым контрактом. Добавить проверки выбора нужного модуля и отсутствия побочных импортов.

**Готово:** общий код зависит от точек входа, а Windows-реализация выбирается в одном месте на предмет. Пустые macOS/Linux-модули с ложным успехом не созданы.

1. Перенести `process_windows.has_window`, Job Object и перечисление потомков из `app_tied_process`, Windows-поиск браузера и привязку `node.exe` в Windows-пакет.

**Готово:** архитектура выделена и доступные проверки проходят; непроведённая нативная Windows-регрессия явно записана и остаётся обязательной до финальной передачи. После этого переходим только к macOS.

### B. Затем macOS: реализация, сборка и проверка на Mac пользователя

Результат этапа — локально собираемый и проверенный `JobBot.app` и ZIP на фактической архитектуре Mac. Настройка CI, поддержка Linux, сертификат Developer ID и нотариализация не блокируют этот результат.

#### [ ] Шаг 5. Проверить локальные инструменты и зависимости macOS

2. Исправить разрешение зависимостей только для macOS, сохранив Windows-установку: убрать Windows-only транзитивные зависимости из macOS lock, добавить PyObjC и macOS backend keyring.
3. Проверить поддерживаемую Pipenv схему для Windows wheel и macOS `llama-cpp-python==0.3.19`. Если единый lock не подходит, добавить в `build_tools/dependencies.py` генерацию macOS-входа из `Pipfile` и отдельный lock. Повторные TOML-ключи и вручную скопированный список пакетов не использовать.

**Готово:** текущий Mac устанавливает macOS-зависимости из фиксированного набора; нативные пакеты импортируются; Windows-lock не сломан. Linux-lock пока не создаётся.

#### [ ] Шаг 6. Подтвердить минимальную упаковку pywebview на Mac

1. Локально создать маленький пример pywebview с HTML, JS→Python-вызовом, событием готовности и файловым диалогом, не импортирующий весь JobBot.

3. Зафиксировать один рабочий вариант в `build_tools/config.toml`. Не поддерживать оба упаковщика без необходимости.

**Готово:** локальный упакованный пример открывается и выполняет вызов моста; дальнейшая macOS-реализация опирается на проверенный упаковщик.

#### [ ] Шаг 7. Реализовать macOS-модуль рабочего стола и окна

**Файлы:** `adapters/platforms/macos/`, macOS-ветви общих точек выбора.

1. Добавить открытие URL/файлов через `/usr/bin/open` и выделение файла через `open -R`; сохранить проверки схем, расширений и каталогов в общем коде. Команды запускать массивом аргументов.

4. Подключить macOS-реализации в общих точках выбора без новых `sys.platform`-веток в бизнес-логике.

**Готово:** на Mac открываются ссылки, запрещённый файл только показывается в Finder, ошибка старта видна, мастер переходит в нормальное растягиваемое окно. Windows-модуль не менялся ради этих операций.

**Готово:** нужные программы находятся вне терминального PATH, отсутствующие компоненты дают понятную диагностику. Finder-проверка конечного `.app` будет повторена на шаге 13.

**Готово:** полный пользовательский путь работает из исходников на Mac, результаты записаны. К Linux не переходим: сначала получить рабочую macOS-сборку.

#### [ ] Шаг 11. Добавить отдельный сборщик с одной новой целью macOS

**Готово:** одна локальная команда воспроизводит macOS-конвейер и явно сообщает ошибки; основной проект не зависит от `build_tools` во время работы.

**Готово:** получен самостоятельный `.app` и ZIP для локальной проверки; ресурсы и нативные компоненты комплектны.

#### [ ] Шаг 13. Локально проверить и принять macOS-сборку

1. Пользователь проверяет `.app` на своём Mac из Finder: чистый мастер, повторный запуск, keyring, браузерный вход/агент, Claude Code вне терминального PATH, GGUF, clipboard, Dock, остановку и аварию. По дефектам фиксировать шаги воспроизведения, без запроса секретов.

**Готово:** пользователь подтвердил работоспособность конкретного `.app` на своём Mac; есть воспроизводимая локальная команда, ZIP и отчёт. Непроверенные версии macOS/архитектуры не заявлены поддержанными. Только теперь начинается этап Linux.

#### Отдельные последующие задачи: подпись macOS и CI

Эти задачи не блокируют переход от локально принятой macOS-сборки к Linux и не требуют подготовки до начала runtime-изменений.

- При подготовке полноценного публичного macOS-выпуска: настроить Developer ID/нотариализацию, подписать вложенные компоненты и `.app`, сформировать DMG, нотариализировать/staple и проверить Gatekeeper и keyring после обновления. Без сертификата выдавать только явно обозначенный pilot; не отключать quarantine автоматически.
- При необходимости автоматизации: перенести уже работающие локальные команды в нативные CI jobs с зафиксированными runners/версиями, кешами по lock и проверкой скачанных артефактов. Не начинать с настройки runners ради локальной macOS-проверки.
- Intel macOS, Linux arm64, AppImage/пакетные форматы и полное самообновление новых ОС — самостоятельные расширения после базовой поставки.

### Команды и контрольные границы

До исправления зависимостей конкретной ОС не применять к ней текущий Windows-lock. На этапе A выполняются архитектурные проверки и доступные тесты; на этапе B устанавливаются только macOS-зависимости; на этапе C — Linux-зависимости.

```sh
# Из корня, Python относится к проверяемой версии/набору зависимостей:
python -m pytest -q -p no:cacheprovider
python -m ruff check .

# Из client/web:
npm ci
npm test
npm run build
```

Сначала запускать затронутые тесты, затем полный набор текущей целевой ОС на границе этапа. Изменение bridge/UI требует Vitest и живой проверки. Общие изменения Linux требуют macOS-регрессии; нативную Windows-регрессию нельзя заменить моками, но отсутствие Windows-машины не требует остановить всю локальную macOS-разработку.

Будущие команды сборщика после соответствующих шагов (сейчас ещё не реализованы):

```sh
# На Mac пользователя после шагов 11–12; target совпадает с его архитектурой:
python -m build_tools doctor --target macos-arm64
python -m build_tools build --target macos-arm64 --profile pilot
python -m build_tools verify --artifact <путь-к-macos-zip>

# Только на Linux после шага 17:
python -m build_tools doctor --target linux-x86_64
python -m build_tools build --target linux-x86_64 --profile release
python -m build_tools verify --artifact <путь-к-linux-архиву>
```

Если Mac окажется Intel, выбрать соответствующий нативный target после проверки зависимостей, а не настраивать arm64-среду автоматически. `verify` отделяет статическую проверку архива от реального запуска; работа на одной ОС не доказывает работоспособность bundle другой ОС.

## 10. Критерии готовности

Критерии применяются последовательно: сначала к macOS на этапе B, затем к Linux на этапе C. На архитектурном этапе A подтверждается выделение Windows-модуля и сохранение прежнего поведения; работоспособность обеих новых ОС сразу не требуется. macOS сначала заявляется только для фактически проверенного Mac; расширение матрицы и проверка на отдельной чистой машине — последующие задачи, а не условие начала Linux.

- На каждой заявленной цели приложение запускается без установки Python и Node.js; мастер создаёт схему БД и сохраняет настройки между запусками.
- Системный keyring действительно сохраняет и возвращает ключ после перезапуска; отсутствие хранилища приводит к видимому объяснению.
- Svelte работает в реальном WebView каждой ОС: мост и события, выбор/сохранение файлов, вставка и копирование, шрифты, модальные окна и изменение размеров. Vitest/jsdom не заменяет эту проверку.
- На чистой БД мастер завершает переход к основному окну: минимум меняется, растягивание доступно, центр сохраняется. Проверены Retina, CSS-autosize, Cmd и повторное открытие через Dock.
- Проходят вход Telegram, сохранение сессии и повторный запуск; LLM проверен через контролируемый endpoint, GGUF — реальным вычислением эмбеддинга из bundle. Claude Code отдельно проверен там, где заявлена его поддержка.
- Агент на тестовой странице открывает профиль, принимает ручной вход, заполняет форму, корректно реагирует на «Стоп» и закрытие браузера. Проверки не рассылают настоящие отклики работодателям.
- После нормального выхода и аварийного завершения нет оставленных собственных процессов или блокировок профиля; если аварийный сценарий ещё не решён, это явно ограничивает готовность.
- Открываются разрешённые ссылки и вложения; ограничения путей/расширений сохранены. Вторая копия не начинает работу с той же БД, первая получает запрос показа окна с учётом ограничений оконной системы.
- Файл с запрещённым для открытия расширением показывается в файловом менеджере без исполнения: Finder выделяет его через `open -R`, Linux показывает через FileManager1 либо родительский каталог.
- Обновление на macOS/Linux не запускает Windows-код и не скачивает exe; переустановка сохраняет данные. Обновление существующей Windows-сборки продолжает работать.
- В артефакте есть все миграции, фронт и нативные runtime-компоненты; личных данных нет. Архив сохраняет права и ссылки, manifest описывает фактическую цель.
- Существующие pytest/Vitest и новые платформенные проверки проходят. В pytest отдельно отделены Windows-only интеграции от общих контрактов, а не отключены общие проверки целиком.

При переносе тестов отдельно разобрать `tests/test_config.py`, `tests/backend/test_single_instance.py`, `tests/adapters/test_browser_choice.py`, `tests/client/test_bridge_shell.py`, `tests/backend/test_updater.py`, `tests/adapters/test_claude_code.py`, `tests/backend/test_bot_update.py`, `tests/backend/test_entry_point.py` и `tests/client/test_window_size.py`. Проверки общих функций параметризовать для платформ, Windows API — маркировать; не скрывать дефекты импорта общим skip всего набора.

## 11. Что остаётся подтвердить реализацией

Наиболее неопределённые участки: установка всех закреплённых версий на Python 3.13, связка GTK/PyGObject, упаковка PyObjC, обычный браузер входа на Wayland и завершение потомков при аварии. Проверки выполняются в начале этапа своей ОС: сначала после выделения архитектуры проверяется macOS на существующем Mac, а Linux — только после локальной приёмки macOS. Они не предшествуют архитектурному этапу и не требуют одновременной подготовки трёх сред.

На исходном исследовательском этапе сборки и тесты приложения не запускались, зависимости не устанавливались. После реализации этапа A выполнен полный pytest-прогон на Mac и статические проверки; фактические результаты и ограничения приведены в отчёте этапа A. Нативные сборки по-прежнему не выполнялись. Выводы о препятствиях основаны на исходниках; предложенные способы переноса сверены с первичной документацией, но требуют прототипов и проверки полученных артефактов. Текущий документ — предложение для контрибьюта, а не заявление о готовой поддержке macOS/Linux.

## 12. Результат сверки со спецификацией macOS

Приняты пропущенные детали: импорт `errno.EDEADLOCK`, Windows-only зависимости lock, переход из мастера через WinForms, показ файла через Explorer, Quartz для наблюдения за окнами macOS, kqueue как кандидат сторожа, конкретный поиск Claude Code из Finder, onedir/BUNDLE/Info.plist, проверка Rosetta, WebKit CSS и Dock. Для адаптеров достаточно функций с одинаковыми именами и выбора реализации в одном месте на предмет; абстрактные классы и реестры не нужны.

Уточнения к спецификации: два одинаковых ключа пакета в TOML недопустимы; установка без lock не подходит для релиза; закрытие `macos-13` не означает исчезновения Intel runners. Утверждения о правах Quartz, доступности wheel и работе окон проверяются прототипом, а не принимаются как гарантия. Неподписанный пилот допустим отдельно от полноценного подписанного выпуска. Полное самообновление `.app` по-прежнему отложено; при его реализации менять нужно весь bundle, сохраняя подпись.

При сверке выполнена только диагностическая проверка `errno` в текущем Darwin/Python 3.15: `EDEADLOCK` отсутствует, `EDEADLK` доступен. Это подтверждает риск, но не заменяет тест на целевом Python 3.13. Исходники приложения и новая спецификация не менялись.
